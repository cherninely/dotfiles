# Global Instructions

## Serena LSP и AST Index — приоритетные инструменты для работы с кодом

При работе с кодом **всегда предпочитай Serena LSP и AST Index** встроенным средствам (Grep, Glob, Read).

### Serena LSP

- **Навигация по коду**: используй `find_symbol`, `get_symbols_overview`, `find_referencing_symbols` вместо Grep/Glob для поиска классов, функций, методов и переменных.
- **Поиск связанных частей кода**: используй `find_referencing_symbols` чтобы найти все места, где используется символ — это точнее текстового поиска через Grep.
- **Понимание структуры файла**: начинай с `get_symbols_overview` перед чтением всего файла через Read.
- **Чтение кода**: используй `find_symbol` с `include_body=True` для чтения конкретных функций/методов вместо Read для всего файла.
- **Редактирование кода**: используй `replace_symbol_body`, `insert_after_symbol`, `insert_before_symbol` для точечных правок.
- **Переименование**: используй `rename_symbol` для переименования с автоматическим обновлением всех ссылок.
- **Поиск паттернов**: используй `search_for_pattern` когда не знаешь точное имя символа.

### AST Index — ориентация в проекте

Используй `/ast-index` когда нужно **найти** код, а не работать с уже найденным:

- Не знаешь, в каком файле определён класс или функция → поиск символа по имени
- Нужно понять, кто вызывает функцию или использует тип → поиск использований
- Нужно найти все реализации интерфейса → поиск реализаций
- Нужно разобраться в незнакомой части проекта → карта модулей, иерархия классов

Нашёл через AST Index — дальше работай через Serena LSP.

### Когда какой инструмент использовать

| Задача | Инструмент |
|--------|-----------|
| Навигация внутри файла, чтение/редактирование символов | **Serena LSP** |
| Найти символ, его использования, реализации, структуру проекта | **AST Index** |
| Файлы конфигурации (JSON, YAML, TOML, .env) | Встроенные (Read, Edit) |
| Markdown, README, документация | Встроенные (Read, Edit) |
| Простые однострочные правки внутри тела функции | Edit |
| Проект не подключен к Serena/LSP недоступен | Встроенные (Grep, Glob, Read) |

## Атомарные PR

Любая работа над кодом оформляется как набор атомарных PR: один PR — одно законченное изменение, которое можно отревьюить и влить отдельно. Правило действует и для больших задач: «сделать всё одной пачкой» — не вариант.

### Нарезка

- Один PR = одна причина для изменения. Фича, багфикс, рефакторинг, переименование, форматирование — всегда разные PR.
- PR самодостаточен: собирается, тесты зелёные, поведение консистентно. Никаких «доделаю в следующем PR» внутри вливаемого изменения.
- Ориентир по размеру — до ~400 строк диффа. Больше — режем: подготовительный рефакторинг → собственно фича → чистка.
- Механические правки (rename, move, автоформат, обновление зависимостей) — отдельным PR, не смешиваются с логикой.
- Зависимые PR выстраиваются стеком: базовый → следующий поверх него; зависимость явно указывается в описании.

### Порядок работы

1. До написания кода — план нарезки: список PR, что в каждом, порядок и зависимости. Дождаться подтверждения пользователя.
2. Делать по одному: ветка от актуального trunk/main → изменения → сборка и тесты → коммит.
3. Не смешивать два PR из плана в одной ветке и не начинать следующий, пока текущий не оформлен.
4. Пуш и создание PR — только по явной команде пользователя.
5. Описание PR: зачем (проблема), что сделано, как проверено, на чём основан / что дальше.
6. Сообщение коммита — императив: одна строка сути + детали в теле; в Аркадии — с ключом тикета в заголовке.

### Инструменты

- Arcadia (`.arc/`, `.arcignore`, корневой `a.yaml`) — только `arc`, PR через скилл `arc` / `create-pr`. Никогда `git`/`gh`.
- Остальные репозитории — `git` + `gh pr create`.
- Параллельные и стековые PR — через `arc-worktrees`, а не переключением веток в основном чекауте.

## Комментарии в коде

Комментировать только неочевидное: «почему так», а не «что делает код».

- Не писать комментарии, пересказывающие соседнюю строку.
- Не ставить шапки-разделители над блоками и не помечать шаги (`# Шаг 1`, `// теперь сохраняем`).
- Не оставлять комментарии о процессе правки («добавлено», «было X, стало Y», «см. новый вариант ниже») — это место для описания коммита или PR.
- Уместны: неочевидная причина решения, ссылка на тикет/багу/спеку, обход чужого бага, нетривиальный инвариант или единица измерения.
- Докстринги и комментарии публичного API — писать, если это принято в проекте.
- Плотность комментариев в правках не выше, чем в окружающем коде.
