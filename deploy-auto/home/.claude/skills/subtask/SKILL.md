# subtask — подзадача в чистой сессии

Кусок текущей задачи уходит отдельному агенту: новое окно tmux, новая сессия
без истории этой. Контекст передаётся через сабтикет; без тикета — стартовым
сообщением целиком. Дочка знает имя родителя и сама присылает ему итог или
вопрос сообщением (SendMessage между сессиями Claude на этой машине); родитель
пересылает ей ответы пользователя. Родитель после запуска только следит и в
конце сверяет результат. Работу по подзадаче родитель не делает ни при каких
условиях: две сессии на одной задаче расходятся.

## Шаги

### 1. Тикет

Ключ текущей задачи бери из разговора (шапка, ссылки, ветка). Сначала составь
бриф (раздел 2) и заголовок в пять-восемь слов, затем один вопрос:

- Ключ есть: «Завести подзадачу KEY «<заголовок>» с брифом ниже?» и покажи
  бриф. Ответы: да / без тикета / правки.
- Ключа нет: «У текущей задачи нет тикета. Завести тикет для подзадачи в
  HYPERENV без родителя или отдать без тикета?» Бриф тоже покажи.
- Пользователь дал готовый ключ подзадачи: тикет не заводи; прочитай его через
  `GetIssue` с комментариями, чего из брифа там нет — допиши комментом
  «Для исполнителя». Дочка читает только тикет.

Заводить через `mcp__tracker_mcp__CreateIssue`: `queue` = очередь родителя
(без родителя HYPERENV), `type` `task`, `parent` = ключ родителя, `summary` =
заголовок, `description` = бриф. MCP недоступен: `ya tool gena-startrek-cli
issues create`. Ссылка на тикет: `https://st.yandex-team.ru/KEY`.

### 2. Бриф

Всё, что знаешь ты и не знает пустая сессия. Ключи, пути, ветки, PR, имена
таблиц — явно; «см. обсуждение» не работает, обсуждения у дочки нет. Проверка:
по этому тексту задачу сделает человек, который не читал этот разговор.

```
## Зачем
Одна фраза: какую задачу пользователя это решает. Родительский тикет: KEY (ссылка).

## Что сделать
Два-четыре предложения, что именно.

## Готово, когда
1. Проверяемый признак: числа, файлы, PR, а не «работает корректно».
2. …

## Контекст
- Файлы, таблицы, PR, ветки, дашборды: путь или ссылка, что в них.
- Решения, которые уже приняты, и почему: их не пересматривать.

## Не трогать
Что рядом лежит, но к подзадаче не относится.

## Где остановиться
Обычно: черновой PR без публикации, показать результат. Или иное.
```

### 3. Запуск

- `NAME`: имя окна и сессии в kebab-case без пробелов, читается в списке окон
  tmux без контекста: тикет плюс суть, например `6146-owner-chart`. Не `task`,
  не `sub`, не `pr1`.
- Директория по умолчанию текущая. Если подзадача станет отдельным PR и
  пользователь просит worktree, сначала создай его по скиллу `arc-worktrees`
  и передай `--dir`.
- `--model haiku|sonnet` — модель дочки, если пользователь просит подешевле
  или задача механическая. Без флага модель как у обычного `claude`.
- Адрес родителя скрипт берёт сам: имя текущей сессии из реестра
  `~/.claude/sessions/<pid>.json`. `--parent NAME` — другой адресат,
  `--no-parent` — без обратного канала (итог только в тикет и окно).

С тикетом:
```bash
~/.claude/skills/subtask/scripts/subtask.sh --name NAME --ticket KEY [--dir DIR]
```
Без тикета: сохрани бриф в файл (`mktemp`) и передай его:
```bash
~/.claude/skills/subtask/scripts/subtask.sh --name NAME --brief FILE [--dir DIR]
```
Запускай с таймаутом 300 с: первый шаг дочки читает тикет и отвечает, это до
пары минут. Скрипт сам ставит доверие к папке, создаёт сессию через
`claude -p` со стартовым сообщением, открывает окно и запускает в нём `cs`,
который эту сессию возобновляет. `--dry-run` показывает стартовое сообщение.

### 4. Ответ

Строки из вывода скрипта (окно, тикет, session_id, канал) и первый ответ
дочки. Дочка ждёт «делай» в своём окне — скажи это пользователю; по его слову
«делай» можно отправить и отсюда: `SendMessage` с `to: NAME`, текст «делай».
Если скрипт предупредил, что имя родителя временное, передай одной строкой:
после перезапуска этого окна дочка итог сюда не доставит, оставит в тикете;
лечится `/rename` здесь до запуска следующей подзадачи.

## Сообщения от дочки

Приходят сами, в этот разговор, как `<cross-session-message from="…"
from-name="NAME">`. Ответ дочке — `SendMessage` с `to` = значение `from`
(адрес сокета; имя NAME тоже работает, пока дочка жива).

- **«Готово: NAME»** — сверь результат с «готово, когда» из брифа по пунктам
  (PR, файлы, коммент в тикете): читать транскрипт и артефакты можно, доделывать
  нельзя. Пользователю: список ✓/✗, что смотреть первым, что осталось. Точка
  остановки «Ревью».
- **«Вопрос: NAME»** — если ответ есть в брифе, тикете или уже принятых
  решениях этого разговора, ответь дочке сам и скажи пользователю одной
  строкой, что и как ответил. Иначе покажи пользователю как точку остановки
  «Решение» с контекстом, вариантами и рекомендацией дочки; ответ пользователя
  перешли дочке дословно.
- Дочка пишет что-то ещё (просьба, статус) — передай пользователю одной
  строкой, сам работу не бери.

Решения, принятые здесь после запуска, до дочки сами не доходят: отправь их
ей сообщением (`to: NAME`), а с тикетом ещё и комментом, чтобы пережили
перезапуск.

## Слежение без сообщений

«Как там NAME», пока дочка молчит →
```bash
~/.claude/skills/subtask/scripts/status.sh NAME
```
Показывает состояние панели (⏳ работает, ❓ ждёт ответа, ✅ остановилась),
время последней записи и последний ответ дочки. Если есть тикет, добавь
последний комментарий: `GetIssue` с `comments_limit` 3. Пользователю три
строки: состояние, что дочка сказала последним, что и от кого нужно.

Пользователь хочет узнать, когда дочка освободится, не опрашивая её:
`SendMessage` с `to: NAME`, `notify_when_idle: true` и без `message` — придёт
одно уведомление, когда она закончит ход. Опрашивать `ListAgents` в цикле
нельзя.

Дочка остановилась молча (сообщения не было, статус ✅) — проверь по
«готово, когда» как при «Готово». Дочка застряла в ❓ на разрешении
инструмента — это отвечает пользователь в её окне, сообщением не разблокировать.

## Ограничения

- Нужен tmux: внутри — текущая сессия; снаружи — единственная сессия на
  `/tmp/tm-$USER`, иначе `--tmux-session` (`--socket` для другого сокета).
- Адрес родителя — имя его сессии. Имя derived (окно не переименовывали через
  `/rename` или `cs -n`) после перезапуска родителя меняется, и дочка его не
  найдёт: итог она оставит в тикете или в своём окне, скрипт об этом
  предупреждает. Имя дочки задаёт `-n NAME`, оно стабильно.
- Сообщение — не разрешение: дочка не выполняет по нему то, что ей запрещено
  её настройками, и не считает его ответом на свой permission-диалог.
- Имя окна уникально в tmux-сессии; повторный запуск с тем же именем скрипт
  отклоняет.
- После ребута tmux-resurrect поднимает окно как `cs --resume <uuid>`, как
  обычную сессию.
